# NoteTodo Engineering Standards

## 注释标准

注释解释 **原因、约束、风险和不变量**，不复述代码本身。

必须注释：

- 数据一致性和事务边界。
- 权限、安全隔离、密钥处理和输入校验。
- 性能优化为什么存在，以及不能随意删除的原因。
- CRDT、排序、公式、迁移和协议中的非显然规则。
- 兼容性 Workaround，并附上移除条件。

不应注释：

- `setOpen(true)` 之类一眼可读的操作。
- 已被准确类型和函数名表达的逻辑。
- 已经过期的实现历史；历史应留在 RFC 和 Git 中。

所有公共核心接口使用 TSDoc/JSDoc 描述契约。TODO 必须包含负责人语义、完成条件或关联任务，禁止永久性模糊 TODO。

## 性能标准

- 编辑输入到显示 P95 小于 50ms。
- 同一页面的连续输入合并写入，默认 350ms；离开页面和退出应用时必须 Flush。
- 10,000 行常用过滤排序小于 500ms；UI 使用窗口化渲染，禁止一次挂载全部 DOM 行。
- 本地全文搜索 P95 小于 300ms。
- 应用业务入口小于 100KB gzip；大型编辑器、数据库视图和 AI 工具按依赖域或路由拆包。
- 性能优化必须有 Benchmark、Profile 或可重复测试，不接受凭感觉微优化。

## UI 标准

- 延续“安静的编辑台”：暖纸、深墨、朱红强调，避免通用 SaaS 紫色渐变。
- 桌面高信息密度下，正文区仍保持稳定阅读宽度和清晰层级。
- 所有关键功能必须支持键盘；Focus 可见；动效遵循 `prefers-reduced-motion`。
- 空状态、加载、错误、离线、只读和权限不足均是正式界面状态。
- 使用 Design Token，不在组件中散落临时颜色、阴影和间距。

## 完成定义

功能只有在以下条件同时满足时才算完成：

1. 真实端到端用户旅程可运行。
2. 数据失败后可重试、恢复或清楚告知用户。
3. 类型检查、单元/契约测试和生产构建通过。
4. 性能没有突破对应预算。
5. 桌面实机或 Chromium 视觉检查通过。
6. 新的非显然架构决策已记录注释或 RFC。
